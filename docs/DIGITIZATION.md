# Оцифровка учебников — как она устроена

Документ для того, кто пришёл в проект и должен понять систему целиком либо
завести новый учебник. Цифры — в `EVAL.md`, журнал работ — в `PROGRESS.md`,
правила и план сессий — в `CLAUDE.md`.

---

## 1. Что система делает

На входе — PDF учебника математики (скан или born-digital, русский или
узбекский). На выходе — записи в `tasks_master`: условие, LaTeX-формулы,
правильный ответ, дистракторы, привязка к навыку. Это то, что видит ученик
в диагностике и в тренажёре.

Ключевое различие, которое стоит понять первым: **оцифровка — это не «PDF →
JSON».** Получить JSON с текстом страниц несложно. Ценность появляется там, где
задача становится пригодной для выдачи ученику: у неё есть проверяемый ответ,
правдоподобные неверные варианты и известно, какой навык она проверяет.

---

## 2. Два слоя, которые нельзя смешивать

| Слой | Что делает | Где ошибается |
|---|---|---|
| **Перцепция** | пиксели → текст и регионы | на глифах: формулы, кириллица внутри формул, сноски |
| **Семантика** | текст → границы задач, ответы, привязки | на структуре: где кончается задача, к чему относится «а)» |

Смешивать их вредно: ошибку перцепции чинят другим DPI и другим промптом,
ошибку семантики — эвристикой по тексту, без единого вызова модели. Когда они
свалены в один шаг, непонятно, что именно чинить.

---

## 3. Конвейер по шагам

```
PDF
 ↓  OCR (Gemini через Vertex AI, батчи по 4 страницы, sliding-window лимитер)
 ↓  Legend → Split → Extract      извлечение задач по листовым параграфам TOC
 ↓  СТРУКТУРА (src/pipeline/structure.py)         ← Сессия 4
 ↓  Validate (SymPy) → Enrich → Distractors → Classify
 ↓  ГЕЙТЫ (src/pipeline/gates.py)                 ← вердикт pass/review/reject
 ↓  СКОРИНГ (src/pipeline/scoring.py)             ← Сессия 5, очередь проверки
 ↓  tasks_staging          (src/pipeline/staging.py)
 ↓  ПРОМОУШЕН              (scripts/promote.py, --dry-run по умолчанию)
tasks_master
```

**Пайплайн управляется оглавлением, а не файлом.** `_run_pdf_page_based` идёт по
листовым параграфам `textbook_toc` и обрабатывает диапазон страниц каждого.
**Нет TOC → не произойдёт ничего**, сколько PDF ни клади. Если после приёма
задач ноль — копать в `textbook_toc`, а не в извлечении.

## 4. Пять инвариантов

Это несущая конструкция. До них качество держалось на дисциплине разработчика,
и ничего в коде ей не соответствовало.

| | Инвариант | Где живёт | Что было без него |
|---|---|---|---|
| И1 | У каждого значения есть источник и уверенность | `provenance.py` | придуманный ответ неотличим от напечатанного |
| И2 | Сгенерированное не перекрывает напечатанное | `answer_key.py` | 3 369 строк валидировали догадку, не зная, что это догадка |
| И3 | В `tasks_master` не пишет никто — пишет промоушен | `staging.py`, `promote.py` | «стало лучше или сломали 200 задач» — ответа нет |
| И4 | Каждая стадия оставляет артефакт по хэшу входа | `artifacts.py` | правка промпта тихо возвращала старый результат из кэша |
| И5 | Согласие маршрутизирует внимание, не сертифицирует | `consensus.py` | два одинаковых ответа модели считались подтверждением |

### И3 на практике

Конвейер пишет в `tasks_staging` — **всё**, включая `reject`. Брак обязан
попасть в карантин: иначе он либо теряется, либо просачивается мимо учёта.
Дальше `scripts/promote.py` переносит в `tasks_master` только `gate_status =
pass`. Аварийный откат на прямую запись — `PIPELINE_WRITE_TARGET=master`,
это не штатный режим и гейты в нём не применяются.

## 5. Три независимых сигнала качества

Одного мало. Замер показал, почему:

| Артефакт | KaTeX ловит? |
|---|---|
| `\left(\frac{14\pi}{3}ight)` — потерян `\` в `\right` | ✅ да |
| `150^\\circ` — задвоенный слэш в степени | ✅ да |
| `x \\cdot y` — задвоенный вне степени | ❌ **молча ок**: `\\` — валидный перенос строки |
| `rac{1}{2}` — потерян `\` в `\frac` | ❌ **молча ок**: рендерится как текст |

Последние два — тихая порча содержания: ученик видит бессмыслицу, а
`compile_rate` показывает 1.0. Поэтому сигналов три:

1. **Компиляция** (`src/validate/katex.py`) — формула физически рендерится;
2. **Лексика** (`src/validate/latex_artifacts.py`) — команда цела;
3. **Структура + провенанс** (`gates.py`) — это вообще задача, и откуда ответ.

**Не трактовать `compile_rate = 1.0` как «формулы верны».**

## 6. Очередь ручной проверки

`needs_review` отвечает на вопрос «что сломано», а не «чего не хватает». Эти два
сигнала разведены намеренно (С5):

* **`needs_review`** — брак: битая формула, лексический артефакт, структурное
  повреждение, разрыв нумерации, отказ гейта. На корпусе прототипа — 3.2%.
* **`awaiting_answer`** — полнота: ответа из книги нет. На том же корпусе —
  2 496 задач из 2 603.

Когда они были одним флагом, в очередь попадало 97% книги, и приоритизировать
в ней было нечего. Разделение не ослабляет гейт: условие промоушена не менялось.

Посмотреть очередь глазами:

```bash
python3 scripts/demo_pipeline.py --viewer ./viewers
open viewers/<книга>.html
```

Один статический HTML: карточки в порядке «сначала худшее», формулы рендерит
KaTeX, не отрендерилось — красная рамка, фильтр «только требующие проверки».

## 7. Как добавить учебник

```bash
mkdir -p textbooks && cp .env.example .env   # заполнить доступ к Gemini
cp /путь/книга.pdf textbooks/

docker compose up -d --build
docker exec content-api alembic upgrade head

docker exec content-worker python /app/scripts/ingest_textbook.py \
  --pdf /textbooks/книга.pdf --title "Алгебра, 7 класс" --class 7 \
  --language ru --country UZ
# выведет job_id; статус — GET /api/v1/jobs/{id}
```

Дальше — проверить staging и промоутить:

```bash
docker exec content-worker python3 /app/scripts/promote.py --run-id <run> --dry-run
docker exec content-worker python3 /app/scripts/promote.py --run-id <run>   # после бэкапа
```

### Грабли (проверено на свежем клоне)

* Нет ни `.env`, ни папки `textbooks/` — только `.env.example`. Создать руками.
* Доступ к Gemini обязателен: либо `GEMINI_API_KEY`, либо Vertex
  (`VERTEX_PROJECT_ID` + `GOOGLE_CREDENTIALS_PATH`).
* **`GOOGLE_CREDENTIALS_PATH` смонтирован в `docker-compose.yml` без дефолта** —
  пустое значение роняет `compose up` даже при работе через API-ключ.
* **`extract_toc` часто врёт на сканах.** Не случайно в `scripts/` лежит шесть
  `insert_toc_*.py` — для реальных книг оглавление заводили вручную.

## 7.5 Граф знаний: что нужно и как загрузить

Без графа задачи некуда привязывать: классификатор ставит первое, что найдёт,
а промоушен останавливается заслоном (см. ниже). На первом живом прогоне книги
все 687 задач сели на единственный демо-навык, потому что локально в графе было
4 узла-заглушки.

**Что выгрузить со staging** (`algo_content`):

```sql
\copy (
  SELECT id, level, parent_id, name_ru, description,
         class_level_start, class_level_end, sequence_order, importance
  FROM knowledge_hierarchy WHERE is_active = TRUE ORDER BY level, sequence_order
) TO 'knowledge_graph.csv' WITH CSV HEADER
```

Достаточно одной этой таблицы: `skill_prerequisites` нужны диагностике, а не
оцифровке.

**Как загрузить:**

```bash
python3 scripts/import_knowledge_graph.py --file knowledge_graph.csv          # проверка
python3 scripts/import_knowledge_graph.py --file knowledge_graph.csv --apply --drop-demo
```

Скрипт проверяет граф **до** записи: уровни только L1–L4, у каждого узла ниже L1
существующий родитель, уровень родителя ровно на единицу выше, идентификаторы
уникальны. Битый граф не пишется и возвращает код 2. `--drop-demo` вычищает
узлы `DEMO_*`, но откажется это делать, если на них уже ссылаются задачи.

**Заслон промоушена.** Если все задачи книги замаплены на один навык (≥20 задач),
`promote.py` останавливается: у настоящего учебника задачи расходятся по
десяткам навыков, а один навык на книгу означает, что графа под классификатором
не было. Снимается флагом `--allow-skill-collapse` — явно, а не молча.

## 7.6 Формат данных: как задача выглядит в базе

Формат задан не нами — он уже лежит в продовой базе (35 202 задачи, выгрузка
2026-09-01), и совпадать с ним обязательно, иначе банк расслаивается на два
несовместимых куска.

| поле | вид | пример |
|------|-----|--------|
| `tasks_master.id` | `{prefix}_{параграф}_{номер}` | `G5_TB_1_1_42_a` |
| `source_reference` | `{textbook_uuid}::{параграф}:{номер}` | `0fd78e9c-…::1.4:14.10.а` |
| `textbook_tasks` | мост книга ↔ задача | `(textbook_id, task_id, para, ex)` |

`prefix` берётся из `exercise_ranges/registry.py`: по умолчанию `G{класс}_TB`,
для книг с конфликтом — свой (`G7_ALG`, `G8_ALG`).

**Идентификатор приводится к ASCII** (`src/pipeline/task_ids.py`). Точка
становится подчёркиванием, `§` и `№` выбрасываются, длинное тире становится
дефисом, кириллица транслитерируется. Это не косметика: в проде **8 020
идентификаторов из 35 202 (22.8 %) содержат не-ASCII**, а подпункт в одной и той
же роли записан то `_85_а`, то `_85_a` — для базы это разные задачи.

`source_reference`, `paragraph_number` и `exercise_number` нормализации **не**
подвергаются: это ссылка на место в книге для человека, и «§ 1.4, № 14.10.а»
должно читаться так, как напечатано.

**Провенанс.** У задач, записанных до введения И1, `answer_source` и
`text_source` равны `unknown` — это признание, а не источник. Отличается от
`absent` («искали и не нашли»). Конвейер `unknown` не пишет никогда: он всегда
знает, откуда взял.

**Столкновение идентификаторов.** Книги одного класса делят префикс (в проде три
учебника 5 класса на `G5_TB`), поэтому промоушен перед записью проверяет, не
занят ли id задачей другой книги, и такие задачи не промоутит, а считает в
`blocked_id_taken`. Молчаливый `DO NOTHING` здесь недопустим: задача исчезла бы,
засчитавшись как записанная.

Привести идентификаторы прогона, снятого до этого правила:

```bash
python3 scripts/reformat_task_ids.py --run-id <id>            # показать
python3 scripts/reformat_task_ids.py --run-id <id> --apply    # записать
```

Скрипт трогает только непромоутнутые строки и отказывается работать, если новый
формат схлопнул бы две разные задачи в один id.

## 8. Как померить качество

```bash
python3 scripts/eval.py --class-level 8          # строка в EVAL.md
python3 scripts/audit_latex_compile.py --class-level 8
python3 scripts/demo_pipeline.py                 # сквозной прогон без API
```

**Прогон книги ≠ разблокировка метрик.** Свежая книга даёт материал для
`compile_rate`, но `task_recall` и `latex_ned` требуют вручную вычитанного
golden (`src/eval/golden/README.md`). Golden генерировать нельзя: эталон,
сделанный той же системой, проверяет систему самой собой.

## 8.5 Сколько это стоит

Расход считается: `usageMetadata` каждого ответа собирается в
`src/pipeline/usage.py`, сводка пишется в лог в конце прогона —
вызовы, токены входа/выхода/размышления и сколько запросов обслужил кэш.

```
расход по моделям:
  gemini-3.5-flash: вызовов 412 (из кэша 88) · вход … · выход … · всего …
  ИТОГО: вызовов 412 (из кэша 88) · токенов …
```

Цены в коде не зашиты намеренно — они меняются и зависят от тарифа.
`usage.estimate_cost(usage, input_per_1m=…, output_per_1m=…)` принимает их явно;
Batch API дешевле вдвое, и это выбор вызывающего.

**Кэш ответов модели** (`src/pipeline/llm_cache.py`) — SQLite рядом с кэшем OCR.
Кэшируются **только успешные** ответы: повтор после сбоя идёт с тем же промптом,
и если бы в кэш попадал отказ, ретрай после 429 доставал бы его навсегда.
Обрезанные ответы (`MAX_TOKENS`) тоже не кэшируются — повтор может дать целый.
Выключается `LLM_CACHE_ENABLED=false`.

Практика первого прогона: предоплаченных кредитов ключа хватило на ~95% книги
в 108 страниц (687 задач с дистракторами). Самая дорогая стадия — генерация
дистракторов, на ней кредиты и кончились.

## 9. Known Limitations

Честный список. Ни один пункт не «почти работает».

**Кириллица внутри формул.** `S_{\text{общ}}`, `V_{\text{цил}}`, `\text{при } x > 0`.
Открытые формульные модели обучены на arXiv и на этом ломаются. Решение —
файнтюн на синтетике, это отдельная фаза. Сейчас разрыв **измеряется**, а не
закрывается.

**Рукописный ввод** — вне скоупа полностью.

**Сканы со сложной вёрсткой.** Многоколоночная вёрстка правится сортировкой
внутри параграфа (`structure.py`), но врезки, вынесенные на поля, и таблицы,
разорванные страницей, остаются проблемой.

**Оглавление на сканах.** `extract_toc` врёт достаточно часто, чтобы для
реальных книг TOC заводили руками. Пока это ручной шаг, а не автоматика.

**`task_recall` и `latex_ned` не измерены ни разу.** Нет вычитанного golden для
G7/G8. Это не дефект кода — харнесс написан и покрыт тестами, — но пока golden
не засеян, две из пяти метрик недоступны, и сравнивать «до/после» по ним нельзя.

**Склейка через разрыв страницы не проверена на живых данных.** Модуль покрыт
синтетическими тестами, но на выгрузке прототипа сработал 0 раз: там у
практически каждого фрагмента был номер. Настоящая проверка — первый прогон
книги через OCR.

**Промоушен ни разу не выполнялся на проде.** Контур собран и прогнан
end-to-end на 6 книгах без БД. Первый реальный `promote.py` без `--dry-run`
должен идти только после бэкапа.
